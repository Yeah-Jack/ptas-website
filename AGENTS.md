# PTAS Websites

## Project Overview

Turborepo monorepo (Bun workspaces) for two German B2B websites, both built with Next.js 16 and Tailwind CSS 4:

- **ptas.de**: PTAS (Personentransport-Abrechnungsservice), billing service for patient transport
- **taxiware.de**: TaxiWare, software for transport companies that bill patient transport themselves (one-pager plus contact and legal pages)

## Architecture

```text
apps/
├── ptas/           # ptas.de (port 3000)
│   ├── app/        # App Router pages (German routes)
│   ├── components/ # PTAS-specific React components
│   └── content/    # Legal texts loaded at build time
└── taxiware/       # taxiware.de (port 3001)
    └── proxy.ts    # www → apex redirect (see Typed Routes)
packages/
└── ui/             # @repo/ui: shared shadcn/ui components, cn(), base theme
    └── src/
        ├── components/
        ├── lib/utils.ts
        └── styles/globals.css
```

Keep brand-specific code (header, footer, pages, metadata, analytics, legal texts) in the app. Only move code to `packages/` once both sites need it.

## Key Commands

Run from the repo root:

```bash
bun install                            # Install dependencies for all workspaces
bun run dev                            # Start both dev servers (3000 and 3001)
bunx turbo run dev --filter=ptas       # Start a single app
bun run build                          # Build all apps (cached by Turborepo)
bun run check-types                    # Type check all workspaces
bun run test                           # Run tests with Vitest (not `bun test`, that is Bun's own runner)
bun run lint                           # Format & lint with Biome (auto-fix)
```

## Code Patterns

### UI Components

- Use shadcn/ui components from `@repo/ui/components/*`
- Icons: `lucide-react`
- Class merging: `cn()` from `@repo/ui/lib/utils`
- `@/*` points to the current app's own folder

```tsx
import { Button } from "@repo/ui/components/button";
import { Card, CardContent, CardHeader, CardTitle } from "@repo/ui/components/card";
import { cn } from "@repo/ui/lib/utils";
```

### Styling Conventions

- Tailwind CSS 4
- Shared theme tokens live in `packages/ui/src/styles/globals.css`
- Each app's `app/global.css` imports `@repo/ui/globals.css` and overrides brand colors (`--primary`, ...)

### Typed Routes

- `typedRoutes` is on in both apps. `next build` checks every `Link` href; `bun run check-types` (plain `tsc`) does not, so build before trusting a link change.
- Don't add catch-all redirects (`source: "/:path*"`) to `redirects()` in `next.config.ts`: typed routes register them as `/[[...path]]`, which accepts every href. Put host redirects in `proxy.ts` instead, as in `apps/taxiware/proxy.ts`. ptas.de's www redirect still has this problem.

### Language

- All user-facing content is **German**
- HTML lang attribute: `de`
- Route names in German (e.g., `/abrechnung`, `/vorfinanzierung`)

## Testing

- Vitest with React Testing Library, configured in `apps/ptas/vitest.config.ts`
- Test files sit next to the code they test as `*.test.ts` / `*.test.tsx`
- Tests run in Node by default; component tests start with `// @vitest-environment jsdom`
- jsdom lacks `IntersectionObserver` and `ResizeObserver` (needed by motion and Radix), so component tests stub them
- Never send real emails or requests: mock `node-mailjet` in route tests and `fetch` in component tests
- Watch mode: `bun run test:watch`

## Adding shadcn Components

Run the CLI from the app that needs the component:

```bash
cd apps/ptas
bunx --bun shadcn@latest add [component]
```

UI primitives are installed to `packages/ui/src/components`, composed blocks to the app's `components/`.

## Contact Form (ptas.de)

- `/api/contact` (`apps/ptas/app/api/contact/route.ts`) sends each request via Mailjet to info@ptas.de and sales.
- For local work, copy `apps/ptas/.env.example` to `apps/ptas/.env.local` and set `CONTACT_EMAIL_TO` to your own address. It replaces both recipients, and `bun run dev` refuses to send without it.
- Never set `CONTACT_EMAIL_TO` in the Azure production environment.

## Legal Texts and Tracking (ptas.de)

- `apps/ptas/content/legal/datenschutz.html` is generated by dsgvoschutzteam.com and pasted in unchanged. Never edit it by hand: change the services in dsgvoschutzteam and paste the regenerated HTML.
- Scripts that need consent (Google Ads) are loaded by the CCM19 consent manager as embeddings configured in the CCM19 dashboard. Never hard-code them in the app, and check `typeof window.gtag === "function"` before calling `gtag`.

## Legal Texts and Contact Form (taxiware.de)

- `/datenschutz` is not live yet. Its text must be generated in dsgvoschutzteam.com for taxiware.de (Azure Static Web Apps hosting, Cloudflare, Mailjet contact form) and saved unchanged as `apps/taxiware/content/legal/datenschutz.html`, loaded like on ptas.de. Until then, link to it via `datenschutzHref` in `apps/taxiware/lib/links.ts`, because typed routes reject a page that doesn't exist.
- `/api/contact` (`apps/taxiware/app/api/contact/route.ts`) sends each request via Mailjet to the PTAS team (info@ptas.de and sales). For local work, copy `apps/taxiware/.env.example` to `apps/taxiware/.env.local` and set `CONTACT_EMAIL_TO` to your own address; `bun run dev` refuses to send without it. Never set it in the Azure production environment.
- taxiware.de has no tracking or consent manager. Update the Datenschutz text before adding any.

## Deployment

Each app is its own Azure Static Web App with its own Azure-generated workflow (`.github/workflows/azure-static-web-apps-<adjective>-<noun>-<hex>.yml`; ptas.de is `...-red-wave-039b6b203.yml`, taxiware.de is `...-nice-bay-081b6af03.yml`).

- The apps use different deployment authorization policies, and each workflow must match its app's policy, or Azure rejects the upload with "No matching Static Web App was found or the api key was invalid":
  - ptas.de uses **GitHub** (OIDC): `id-token: write`, a "Get Id Token" step and `github_id_token` are required.
  - taxiware.de uses **Deployment token**: only `azure_static_web_apps_api_token`. Don't add `github_id_token` unless the policy is switched to GitHub in the Azure portal (Settings → Configuration).
- Never rename these files or move them out of `.github/workflows/`. Azure links each app to its workflow file, and with the GitHub policy it identifies the target app from the filename in the OIDC token.
- Don't move the deploy step into a reusable workflow (`workflow_call`), since that changes the workflow named in the token.
- Shared build steps live in the composite action `.github/actions/build-standalone`. It builds one app with Turborepo and flattens the Next.js standalone output.
- Each deploy workflow is filtered to paths that affect its app.
- `ci.yml` lints, type checks, tests and builds everything.
